# TankCraft

一个用 **Godot 4.7.2** 写的 2D 坦克建造对战游戏。俯视视角，极简霓虹风格。

玩家在网格上从零搭一台坦克：先铺**平台**，再挂**行进机构**，最后堆**功能模块**。炮弹不是凭空出现的——它要被**制造、被输送、被装填**，所以「内部物流布局」和「外形武器」同样重要。打掉对手一段甲板，可能让他的整条弹药管路失效。

> **当前状态：可运行的实现原型，尚未发布。** 核心玩法（建造 / 物理 / 弹药网络 / 战斗结算 / AI / 波次生存）均已实现并有 28 项自动化 smoke 测试覆盖；**Windows release exe 已能一键构建并已 headless 实跑通过**（见「构建 release exe」）。**真人试玩由用户持续进行**（本项目几乎所有缺陷与需求都来自用户实机试玩）；**AI 侧的验证手段是 headless 测试 + 脚本驱动截图 + 像素比对**，不是人工试玩。**没有产出过任何 APK**。

## 玩法概览

### 单人：波次生存（`survival_battle`）

肉鸽式波次生存。每波有时限，活到计时归零即通过。

- 地图上散布**可摧毁的房屋**（撞击或炮击）与**可碾过的坦克残骸**，是战斗期的金钱与经验来源。
- **击毁敌人、摧毁房屋都会给金钱、经验，并按概率掉落配件**（v3.43 起这两条产出都会在屏幕上显示：绿色「+N cr」漂浮数字 + 掉落的模块名；两条掉落线各有保底次数，连续多次没掉时下一次必掉）。
- **金钱产出（v3.44 上调）**：击杀普通敌人 60 cr、击毁房屋 85 cr、碾房屋残骸 28 cr、碾坦克残骸 22–65 cr、Boss 460 cr；**另外每打完一波会结算一笔与战绩无关的奖金** `120 + 40 × (波次 − 1)`（第 1 波 120、第 5 波 280），波间商店页顶部会写明「本波结算 +N cr」。这样做的原因是：原先的收入**全部**来自「打中东西」，而打中东西本身要求坦克完好 —— 坦克一残收入就同步下降，越残越穷，补不回被击毁的模块。
- 敌人**分级别**：招募 / 老兵 / 精英 / 王牌，级别越高结构越复杂。
- 每次升级弹**三选一送配件**的菜单，可顺带进**改装**。
- 波间进**商店**：6 件商品、花钱刷新、出售库存、改装。
- 每 5 波一个 **Boss**。
- **战斗期不允许改装**。驾驶舱被毁即本局结束。

### 对战：1v1 对机器人（`match_battle`）

固定竞技场内的 1v1 对战，双方各一台坦克，击毁对方驾驶舱获胜。

## 建造系统

坦克分**三层**，逐层搭建，选中一层时其余两层变暗且不可操作：

| 层 | 内容 | 说明 |
| --- | --- | --- |
| **行进机构层** | 履带、防弹轮组、机动轮组 | 决定速度与转向 |
| **平台层** | 不同形状的平台模块 | 相当于甲板/地基，模块必须装在平台上 |
| **功能模块层** | 引擎、弹药工厂、弹药库、改进器、炮管、护盾、维修装置、弹药管路、喷射系统 | 决定怎么打 |

两个全局约束：**信用点预算**与**质量上限**。

**驾驶舱是结构锚点**：甲板被打断后，只有仍与驾驶舱连通的部分存活，其余立即解体。

### 模块与管路

模块的端口方向随 `rot` 旋转，改装页会画出**输入/输出箭头**（青色 `in` 指内、琥珀 `out` 指外），方便规划流水线。

弹药管路共六种：

| 管路 | 行为 |
| --- | --- |
| 直管 | 唯一通路 |
| 四分之一弧 | 唯一通路，转 90° |
| 二分之一弧 | 唯一通路，跨 2 格；形为**向内鼓的弧形**（`sin²`，鼓幅半格），两端切线沿管轴，**不是 180° 半圆** |
| 一分二（Tee） | 轮询交替喂两侧 |
| 二合一（Merge） | 两路合流，`in0` 优先但不会饿死 `in1` |
| 四通（Cross） | 两条车道交叉互不干扰，`in0`→`out0` / `in1`→`out1` 直通优先 |

> **注意**：四通不是分流器，它的语义是「两条线交叉」。**想让一路弹药喂两门炮，请用一分二。**

### 弹药与升级

- 弹药按口径分五档：**20 / 40 / 76 / 120 / 155 mm**。口径越小制造越快、基础伤害越低，占用弹药库槽位越少。
- **改进器**让流经的弹药携带升级（伤害、弹速、爆炸、灼烧、减速、延迟爆炸、护盾穿透、穿透、分裂），升级**逐发携带**，不是整台坦克共享。
- 改进装置分**两族**（v3.41）：**通用容器** `改进器·基础/进阶/高级`（1/2/3 个槽，槽里装什么由你决定）；以及**功能固定的模块**——**爆破模块**（自带爆炸）、**火焰模块**（自带灼烧）、**增伤模块**（自带 +18% 伤害）。后三者自带的那条升级**不占槽**，装上就生效，还余一个槽可以再配。


**有效射速 = `max(craft_time_s, reload_s)`**：炮管拿不到弹就无法装填。

- **「启动即最大化」仍然成立，但只在第一次运行时强制** —— 一旦你显式选了「窗口化」或「全屏」，游戏就尊重你的选择，不再改回最大化。

## 运行

### 环境要求

- **Godot 4.7.2 stable**（`4.7.2.stable.official.ed1daf0bf`）——用 4.x 特性，**不兼容 3.x**。
- Windows 桌面为主要目标；架构上保留 Linux / macOS。**移动端触屏只有设计、代码零实现。**

### 启动

```bash
godot --path .
```

窗口启动即最大化（`WINDOW_MODE_MAXIMIZED`），设计分辨率 1920×1080，等比缩放并保留黑边。

### 截图钩子（用于回归比对）

```bash
godot --path . -- --capture=out.png --screen=survival --steps=420 --cursor=960,540
```

`--screen` 可取：`drive` / `build` / `match` / `survival` / `survival_levelup` / `survival_shop` / `survival_summary` / `survival_modify`。

`--steps=N` 预热固定步数（让画面可复现），`--cursor=x,y` 把鼠标钉到指定设计坐标（`--capture` 路径本身不产生鼠标事件），`--zoom=<读数>` 钉住战斗页的相机距离（**语义在 v3.40 变了**：现在填的是**相机读数 1.00–4.00，1.00 = 整图**；旧版是「倍数 0.5–4.0」，旧命令 `--zoom=0.5` 现在等价于 `--zoom=1.0`），`--blueprint=<res:// 路径>` 在进页面前把指定蓝图读进 `builder`。

**`--capture` 必须不带 `--headless`**：`_capture_next_frame()` 依赖 `await RenderingServer.frame_post_draw`，而 headless display server **不发这个信号**，于是 `CAPTURE_OK` 不打印、文件不生成，进程跑到 `--quit-after` 自然退出（看起来像「钩子没被调用」）。加 `--quit-after <帧数>` 自动退出，**单位是帧不是秒**（试驾页 1200 帧够，生存 / 对局页 1600 帧够）。

### 构建 release exe

```bat
build_release.bat
```

产物有两个：**`build/windows/TankCraft.exe`**（单文件，pck 已内嵌，可直接运行）和 **`build/windows/release/TankCraft-<version>-win64.zip`**（可分发压缩包，内含同一个 exe）。

| 参数 | 作用 |
| --- | --- |
| （无） | 构建 release 版 |
| `--debug` | 构建 debug 版（含控制台包装） |
| `--out <路径>` | 指定输出路径（支持含空格的路径） |
| `--godot <路径>` | 指定 Godot，建议指向 `*_console.exe` |
| `--install-templates` | 下载并安装匹配版本的导出模板（**只取 Windows 条目，约 69 MB**，不下载 1.28 GB 整包） |
| `--help` | 显示帮助 |
| `--no-zip` | 只产出裸 exe，跳过 zip 打包 |
| `--zip` | 显式声明要打包（默认已开启，写不写都一样） |

退出码：`0` 成功 / `1` 用法错误 / `2` 找不到 Godot / `3` 缺导出模板 / `4` 导出失败 / `5` 产物缺失 / `6` 模板安装失败 / `7` 打包（zip）失败。

> **前置条件**：必须先装 Godot **导出模板**，且版本与引擎严格一致。脚本默认**不会**自动安装（模板装在 `%APPDATA%`，属工程目录之外），缺失时以退出码 `3` 结束并打印精确路径与三种解决办法。
>
> **当前状态：已实测可产出。** v3.51 实测（`build_release.bat` 在真实 `cmd.exe` 中运行）：`build\windows\TankCraft.exe` **109,969,936 B（104.88 MB）**，SHA256 `a7d06f3b87cd735c42766dbc4d72ddd570449cd926bd786475ef0b2c42b5fae8`；`--debug` 版 **103,733,856 B**。zip 包 `TankCraft-ed3a943-dirty-win64.zip` **38,702,496 B**，包内只有 1 个条目 `TankCraft.exe`，解压后字节数与 exe 完全一致。PE 为 `PE32+` / `x86_64` / `SUBSYSTEM=2 (WINDOWS_GUI)`，尾部带 `GDPC`（pck **内嵌**）⇒ 单文件。
>
> `--install-templates` 会把模板装到 `%APPDATA%\Godot\export_templates\<版本>\`（**工程目录之外**），因此脚本默认**不**自动安装，必须显式传该开关。它走 ZIP central directory + HTTP Range，**只取 4 个 Windows 条目（压缩后 69 MB）**，不会下载 1.28 GB 整包。
>
> **已在真实桌面（带窗口）运行过。** v3.51 把 zip 解压后直接 `Start-Process` 启动包内的 `TankCraft.exe`：进程持续存活，输出 `WINDOW_MODE mode=2 size=(2482, 1417)`（最大化窗口），随后手动结束。`build/` 已被 `.gitignore` 忽略，**exe 与 zip 都不在仓库里**。
>
> **zip 版本号从哪来**：依次尝试 `project.godot` 的 `config/version` → `git describe --tags --always --dirty` → 字面量 `dev`。当前 `project.godot` **没有** `config/version`、仓库也**没有任何 tag**，所以实际得到的是短提交哈希（带未提交改动时追加 `-dirty`）。debug 包名额外带 `-debug` 后缀，不会覆盖 release 包。包目录跟随 `--out`：默认在 `build/windows/release/`，自定义 `--out a\b\g.exe` 则落在 `a\b\release/`。

> `part_destroy_smoke` 是**「模块被打掉之后功能必须失效」这条需求唯一的自动化判据**：它直接驱动 `DamageSystem.apply_part_damage()` → `Duel.bank_of()` / `network_of()` / `can_fire()` / `fire()`，断言被打掉的炮管离开索引、最后一个炮管没了就打不出炮弹、幸存炮管装填进度不丢、制造装置消失后网络里也没有它；另有 7 项源码扫描守住三页的 `part_debris` 接线与「碎片绘制不得引入随机源」。
>
> `selfcheck_smoke` 是**门禁而不是普通测试**：扫 `tests/*.gd` 的全部 `func _check_xxx(` 定义，逐行统计**调用点**（跳过空行、`#` 注释行、定义行），调用点为 0 即打 `SELFCHECK_UNCALLED <file>::<name>` 并计为失败；反向要求 `defs >= 120` 防止「一个都没扫到」假装全绿。**为什么需要它**：v3.44 一轮修了 9 个睡觉的验收、审核又查出 1 个、v3.46 门禁首跑又抓出 1 个 —— 两轮都靠「人手数一遍」才发现。当前 `defs=128 called=128`。
>
> `drive_feedback_smoke` 实例化真实 `main.tscn` 进试驾页，把坦克摆到贴边并给一个朝墙的速度，逐固定步长断言「撞墙产生伤害 / 命中闪光被置位 / 动效层出现 `-N` 承受语义的伤害数字」。**它存在的理由**：试驾页的弹丸永远打不到发射者自己，所以「命中反馈」这类改动若写错分支，静态截图完全看不出来。该测试已用**变异测试**证明非空转（删掉产品代码里的推入调用后立即失败），详见 `docs/design.md` §11.4.2.15。
>
> `pipe_geometry_smoke` 对**六种管道 × 四个朝向**做 **163 条**几何断言：端口必须落在**格边中点**、相邻模块的端口点必须**精确重合**（不给容差）、**弧管中心线的首尾必须逐字节等于 `PipeView.port_point()`**、**弧管端点切线必须沿管轴**（`\|dot\| ≈ 1`，容差 0.03 由 32 段离散化推得）、弧上采样点必须落在**占位包围盒内**（容差半格）且确实有凸起、汇流臂端点必须两两分开。它**另有一条反向对照**：用旧实现那种「首格中心 → 末格中心」直线插值在四分弧上取点，最大偏离 `2.3431 px`（正好是弦高 `r(1−cos45°)`）。**v3.35–v3.38 曾因断言方向写反而假绿**：第 ③ 条断言的是「切线**垂直**于所在格边」——**把错误行为写成了期望值**；第 ④ 条又用自己算的圆心 + 写死的 `CELL * 0.5` 半径，与实现**两边同错、恒过**；而且**完全没有「中心线首尾 == 端口点」这条断言**。三处叠加，四个版本全绿而产品是坏的。**v3.39 已修正并做两次负向验证**（把圆心改回格中心 → 8 条 `arc_start_not_axial`；把首尾缩回半格 → 8 条 `centre_line_head_not_port … gap=8.0000`），详见 `docs/design.md` §11.4.2.19。**两条探针纪律**：容差必须从离散化阶数推（弧是 16 段折线，首尾弦偏差 `sin(90°/16/2)=0.0491`；`sin²` 曲线 32 段时 `\|dot\| ≈ 0.995`）；探针**不得复用被测实现的内部推导**，否则两边同错也会通过。
>
> `conveyor_showcase_smoke` 读入 `data/blueprints/conveyor_showcase.json`（专门为看管道做的展示车），断言六种管道齐备、每个管道件都有非空中心线、`connected_sides()` 同时产出「接上」与「没接上」两种端口，然后驱动 600 个 tick，断言「汇流类里 forward 弹药的 `exit_port` 永远非空」「段内 / 段末 / 阻塞三态都观察到」「至少投递成功一次」。**它守的是一个曾经会撒谎的字段**：`exit_port` 早期把「下游现在能不能收」也当判据，管道一满就变空串，画面上弹头立刻失去方向。详见 `docs/design.md` §11.4.2.16。
> `cannon_view_smoke` 对炮管做 57 条断言：**实时指向的逆换算**（钩子算出的局部角加回车体朝向必须精确等于 `muzzle_dir()` 的世界角，四个不同 `heading` 各测一遍，并带一条**反向对照**证明「不减朝向」会错）；`aim_steps` 是「是不是炮管」的唯一判据（带「有 `caliber` 但不是炮管」的反例）；三条几何不变量（制退器必须跨过半格点、管身长细比 `>= 3.0`）；`mouth_offset()` 的尺寸补偿只拉长不缩短；`_cannon_key()` 唯一性。**它还有一条直接审查 `main.gd` 非注释代码行的断言**——因为 v3.37 那个「炮管被甩到车身之外」的缺陷是**平移**错、所有方向都对，纯几何断言根本抓不到；这条断言已做**两次负向验证**（把 bug 放回去必报 `offset_no_second_centroid_subtract`）。详见 `docs/design.md` §11.4.2.17。
>
> `camera_zoom_smoke` 对战斗场景相机做 **594 条断言**（v3.40 相机改成**距离模型**后整份重写；v3.42 接引擎 `Camera2D` 后新增几何断言组与接线断言组，545 → **594**）：最远档 `camera_at_height(arena, 任意 focus, arena.size.y)` 必须返回**同一个 `Rect2`**（不是等值，这是默认像素不变的构造性保证）；**核心是「相机永远不超出竞技场」**—— 5 个 focus × 13 个距离（含 `FAR*2` / `FAR*1.5` / `99999` 这种**非法越界输入**）下相机四边都在竞技场内、尺寸不超过竞技场；宽高比永不改变且相机恰好铺满视图；6 个距离 × 6 个世界点的 `to_screen → to_world` 往返一致；相机中心恒映射到视图中心；两端点可复算（**最远一格 9.5 px、最近一格 38 px**）；读数换算 `camera_mag` / `camera_height_for_mag` 的边界（`mag < 1` 一律折成最远）；滚轮步进在读数维收敛；一条**负向对照**（**独立重算**旧 0.5× 公式，断言它必须溢出竞技场）；真实 `TankBody` + `CannonBank` 在 4 个距离下的瞄准精度。**它还有一条直接审查 `main.gd` 源码的断言**：`_aim_with_mouse()` 必须把 `camera` 传给 `_aim_player_cannons()`；v3.42 另加 `_paint_battle_world()` 必须**先 apply 相机再 blit** 的接线断言。**核心断言已做负向验证**：把最远保护去掉后报 **62 条失败**（`far_identity_double`/`far_identity_huge` + 60 条 `inside_*`/`not_wider_*`/`not_taller_*`），恢复后回到 **594** 且输出逐字节相同。详见 `docs/design.md` §11.4.2.20 与 §11.4.2.22。

## 架构要点

- **单场景架构**：所有页面都在 `scenes/main.tscn` + `scripts/main.gd` 里，`change_scene()` 被禁止。
- **数据驱动**：模块定义、价格、质量、建造时长、装填时长、后坐力、AI 参数、射程全部来自 `data/*.json`。代码里不写魔法数字。
- **确定性**：60 Hz 固定步长；只有固定步长累加器驱动逻辑，**绝不对 `dt` 做缩放**；绘制与逻辑中**不用 `randf` / `randi`**（闪烁用 `sin(_time * …)`，随机用显式种子的 LCG）。同一 `--steps=N` 连拍应逐字节相同。
- **弹药网络独立步进**：`ammo_net_hz = 20`，每段管路容量 1 发，与物理帧解耦。
- **两段式炮管装填**：`_accept()` 只登记「待装填」，真正入膛由 `fill_cannons()` 调 `CannonBank.load_round()` 完成。

## 已知限制

以下都如实记录，不是待办清单的包装：

- **真人试玩一直在进行，由用户执行。** 本项目的工作方式是「用户试玩发现 → AI 定位修复」，几乎所有缺陷与需求变更都来自用户实机试玩（UI 分叉、生存模式卡顿、准星错位、标题重叠、炮弹无伤害、转向难控……）。**AI 侧的验证手段是** headless 测试 + 脚本驱动截图 + 像素比对，**不包含人工试玩**——这两件事不能混为一谈。具体到某一项改动，可以说「尚未经过用户实机确认」，但不能说「没有人玩过」。
- **从未在 Android 设备上验证过任何内容，且不存在任何 APK。** 导出预设已写入工程，但本机缺导出模板与 Android SDK。
- **移动端触屏只有设计、代码零实现。**
- **`main.gd` 是上帝类**（`File.Read` 口径 **4,795 行** / **251,726 B**；`(Get-Content).Count` 会报另一个数字，因为两者对空行与末行的统计方式不同，**以 `File.Read` 的 `total_lines` 为准**），按页面拆分被明确搁置。
- **战斗页相机不能旋转、不能拖拽平移。** 滚轮是**推拉**（v3.40 重做完）：范围 **1.00×（整图）– 4.00×**、步进 1.15、`Z` 拉回整图。**最远的极限就是整张地图恰好铺满视野**（一格 9.5 屏幕像素，零空白）；**没有「比整图更远」的视角**（v3.38 的 0.5× 那一档已永久删除——它会让相机比地图还大、视图 75% 是空白）。最近是一格 38 屏幕像素。**相机永远不超出地图**，因此**贴边时焦点会被夹住、车不在画面中心**（这是「不越界」优先于「永远居中」的取舍）。**相机读数不进存档、不是设置项**，切页会复位成 1.00×（整图）。
- **生存掉落数值是按伤害与波时限算出的估计，不是实测手感。** `house_hp = 120` / `house_armor = 3` / 掉率 0.70 与 0.35 / 保底 3 与 4 都是本题的计算值；若实机仍偏硬或偏软，只改 `data/globals.json` 即可，不动代码。
- **生存模式的收入数值是按模块价格与波次配额算出的估计，不是实测手感。** 单波**理论最高**收入 wave1 约 942 cr / wave5 约 1182 cr（旧值 542 / 702），但那要求「配额敌人全杀 + 4 栋房全拆 + 10 处残骸全碾」同时达成；真人实得按 45–55% 折扣只是**推算**（约 470–570 cr/波），headless 无法验证「够不够补」。过波奖金基线与递增率、五项单价都只改 `data/globals.json`，不动代码。
- **四通单源接两出口只喂一侧**——这是设计语义（直通优先），不是缺陷，但**没有 UI 说明**。
- **改进器容量是设计值**：mk1 最多同时容纳 2 发（1 加工 + 1 排队），其余在上游管道排队，不是阻塞。
- **生存模式高波次仍偶发超预算**：wave12 有约 **36/900 步（4%）**单步超过 16.67 ms（p99 19.0 / max 21.7 ms）。碰撞层已从 O(n²) 改为空间分桶（`docs/design.md` §11.4.2.14），但补兵时 `spawn_enemy_us` 仍有 2.6–10.7 ms 的单帧尖峰；而且**只测了逻辑层，绘制层未测**。
- **release exe 已能构建，并已在真实桌面（带窗口）启动过（v3.51）。** `build\windows\TankCraft.exe` **109,969,936 B（104.88 MB）** / SHA256 `a7d06f3b…b5fae8`，`--debug` 版 103,733,856 B，PE 为 `PE32+` / `x86_64` / `SUBSYSTEM=2` 且尾部带 `GDPC`（单文件内嵌 pck）。实跑证据：`Start-Process` 启动后进程持续存活、输出 `WINDOW_MODE mode=2 size=(2482, 1417)`，从 zip 解压出来的那份 exe 同样能启动。仍然成立的部分：`build/` 被 `.gitignore` 忽略，**exe 与 zip 都不在仓库里**；`--install-templates` 的 **`-All` 整包分支从未跑通**（只验证了默认的「只取 Windows 条目」分支）。
- **桌面 exe 的人工启动验证范围有限（v3.51 更新）**：已能启动并进入最大化窗口，但**只观察到窗口创建与进程存活**，未遂个页面点击验证、未做长时间游玩。Android 仍无 APK。**注意：这一条讲的是「exe 的启动验证不够深」，不是「游戏没人玩」——游戏本身一直由用户实机试玩。**
- **蓝图现在会保存改进槽配置（v3.46 修复）。** 此前 `_serialize_parts()` / `_parse_part()` 都不处理 `upgrades`，改装页配好的改进槽「存盘即静默丢失」（`Ctrl+S` 提示保存成功、`Ctrl+O` 提示读回成功，**但槽位是空的**）。现在序列化写出 `upgrades`（**空数组也写**，圆程逐字节稳定）、反序列化走与建造期**同源**的校验（未知 id 丢弃 / 超槽截断 / 按 `stack_limit` 去重，**非法项不整条失败**）。**尚未经过用户实机确认**，尤其「存盘 → 重启 → 读回，槽位还在」这条端到端链路目前只有 headless 证据。
- **商店稀有度权重语义已纠正（v3.46）。** `shop_rarity_weight = [60, 30, 10]` 旧版被当成**价格倍率**用、而抽取是全池均匀的（「稀有商品」名不副实）；现在真的是**抽取权重**（实测占比 **0.602 / 0.301 / 0.098**）。**成交价没变**（新增 `shop_tier_price_multiplier` 默认全 1.0），变的是**哪些商品会出现** —— 低价普通件（尤其 6 cr 的六种 conveyor）明显更常见、史诗件更少见。要按档调价就改那个倍率数组，**不要改权重**。
- **生存难度阈值已进 data（v3.46）。** 敌人升档波次不再写死在代码里，改读 `data/globals.json` 的 `survival.tier_wave_thresholds`（默认 `{"recruit":1,"veteran":5,"elite":10,"ace":15}`）。**默认值与旧的写死值完全等价**，所以本次搬进 data 没有顺手改难度；以后调难度只改 JSON，不动代码。
